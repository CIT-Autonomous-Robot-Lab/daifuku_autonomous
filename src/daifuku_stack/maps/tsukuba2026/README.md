# tsukuba2026 - GLIM 実測点群からの地図

`~/Downloads/glim01.ply` と `glim01.pcd` を読み取り専用で変換した。
両方とも同じ 2,914,091 点の XYZI データなので、重複加算していない。
PCD の宣言点数の後にある 3,904 バイトのゼロ埋めは点として扱わない。
ファイル全体と有効点列の SHA256 は `conversion.json` に記録している。
元の PCD・PLY は変更していない。

## 地図と座標

- 0.1 m/セル、3029 x 2777 セル、302.9 m x 277.7 m。
- 原点は `[-76.4, -177.9, 0.0]`。点群の XY を回転・平行移動せず保持した。
- PGM の上端が地図の Y 最大。PNG は対応する PGM と画素単位で同じ。
- 0 が占有、205 が未観測、254 が自由。未観測を自由へ読み替えない
  `free_thresh: 0.196` を使う。
- `navigation.pgm` は推定地面から高さ 0.275..2.5 m の障害物を投影。
- `localization.pgm` は高さ 0.275..5.5 m の側面・構造物を投影。
- 同名の YAML が map_server 用メタデータ、PNG がフォト等での表示用。

地面は、Z <= 1.0 m の点から 0.5 m 格子内の下位 10% を取り、3 点以上ある
格子を支持点として最近傍補間と 5 x 5 格子の opening で推定した。
その地面から 0.15 m 以内に観測点があるセルを自由空間の根拠とし、
半径 0.2 m の closing で小さな観測の隙間だけを補った。障害物が優先する。

観測軌跡や各ビームの発射位置はないため、射線による自由空間更新ではない。
建物内部や大きな未観測部分を白く塗り潰してはいない。地面分類と通行可能性は
現地で確認が必要で、全コースの経路連結や実走行成功を示す地図ではない。

**2025 の VTC 地図・ウェイポイントとは別座標系。** 2025 の順路をコピーしない。
2026 の経路は別途、この GLIM 座標系で作成する。

## 再生成

リポジトリルートで実行する。Python の依存は `tools/maps/pyproject.toml` にある。

```bash
uv run --project tools/maps python tools/maps/cloud_to_map.py \
  "$HOME/Downloads/glim01.ply" --equivalent "$HOME/Downloads/glim01.pcd" \
  --output src/daifuku_stack/maps/tsukuba2026 \
  --resolution 0.1 --ground-ceiling 1.0
```

## 独立した PGM ノイズ除去

点群の再変換とは別に `tools/maps/denoise_pgm.py` を実行する。
今回の地図では、8 近傍で連結した占有成分が **8 セル以下**のときだけ、
該当セルを 205（未観測）へ戻す。スクリプトは指定値未満を除くため、
`--min-component-cells 9` を使う（スクリプト単体の既定値は 3）。
自由空間や既存の未観測セルは変えず、元画像は上書きしない。
実物の細い物体かノイズかを判別する処理ではないため、閾値を大きくするほど
小さな構造物も自己位置推定用の特徴から外れる。

```bash
uv run --project tools/maps python tools/maps/denoise_pgm.py \
  src/daifuku_stack/maps/tsukuba2026/navigation.pgm \
  src/daifuku_stack/maps/tsukuba2026/navigation_denoised.pgm \
  --min-component-cells 9
uv run --project tools/maps python tools/maps/denoise_pgm.py \
  src/daifuku_stack/maps/tsukuba2026/localization.pgm \
  src/daifuku_stack/maps/tsukuba2026/localization_denoised.pgm \
  --min-component-cells 9
```

出力の PNG は処理済み PGM と同じ画素。JSON に除去セル数と入出力 SHA256 を残す。
自己位置側は `localization_denoised.yaml` を選ぶ。計画側は次の地面補間も行う。
原画像と処理済み画像の解像度・原点・大きさは同じ。

## ナビ用だけの地面補間

点のあるセルだけを白にした原地図では、白は 5.01% で、保守的な 2 x 2 縮小後は
3.74% だった。小さな地面観測の欠けで通路が切れるため、利用者の指定により
ナビ用だけ、半径 0.5 m の closing で局所的な穴を補間した。
新たに白にするのは元の白セルから **0.3 m 以内の未観測セルだけ**。
黒セルは変えず、元の白セルも減らさず、外側全体を膨らませる dilation はしない。
自己位置用の地図にはこの補間を適用しない。

```bash
uv run --project tools/maps python tools/maps/fill_ground_free.py \
  src/daifuku_stack/maps/tsukuba2026/navigation_denoised.pgm \
  src/daifuku_stack/maps/tsukuba2026/navigation_connected.pgm \
  --resolution 0.1 --closing-radius 0.5 --support-radius 0.3
```

補間した 174,174 セルを含む `navigation_connected.pgm` とその YAML は
手修正前の保存地図として残す。この段階の白は 7.08%、
縮小後は 6.07%。縮小後の最大 4 近傍連結領域は約 1,338 m² から約 3,482 m² に増えた。
これはラスタ上の連結性であり、VI の経路成功や車体の走行試験の結果ではない。
新たな観測や射線推定ではなく、既存の地面観測に近い範囲での補間である。

GLIM 原点 (0, 0) の 2 x 2 区画には観測した黒セルがあるため、その区画は
保守的縮小後も通行不可。障害物を消して原点を白くすることはしていない。
実際のロボットの初期位置は、この点群の原点と同一とは限らない。

## 市役所周囲のナビ用手修正

手修正した全域地図は `navigation_reviewed.yaml` として残し、計画側はその画素を
市役所周辺へ切り出した `navigation_cityhall.yaml`、自己位置側は従来の
`localization_denoised.yaml` を選ぶ。自己位置地図と手修正前の地図は変更していない。
2025 の建物・固定物配置を近似位置合わせして照合し、削除範囲は 2026 点群の
高さと形状から世界座標のストロークとして指定した。

北側・北西側の繰り返す帯状リターンは高さの 95% 点が約 1.65 m で、
外壁や柱のように高い位置へ続かない。人やセンサー保持者の残像と整合する候補を
ナビ用だけ除去した。南側の柱間にある低い断片も個別に確認した。
元データは XYZI で時刻列がないため、時間追跡による動体判定ではなく手動分類である。
外壁・柱・低い連続境界・植栽・枠状設備と、判別の難しい高い返りは保護した。

通路の補修は、目視した歩道ストローク内の未観測セルに限る。
元の地面支持に加え、同じ地面推定で高さ ±0.275 m までの低い実測床面を
補助支持へ戻した。障害物が優先し、元の黒セルを支持点には使わない。
補間距離は支持セルから最大 1.2 m。建物内部・固定物保護域と、指定通路外は保つ。
ナビの地図座標・解像度・大きさと、ライブスキャンの高さ帯は変えていない。

- `navigation_manual_edits.json`: 手動範囲、固定物保護域、高さの確認値、入力 SHA256。
- `navigation_reviewed_edit_mask.png`: 0 は無変更、1 は元の黒を自由へ、
  2 は元の未観測を自由へ変更。元 PGM の非ゼロマスク位置だけを 254 にすれば再現できる。
- `navigation_reviewed_protected_mask.png`: 画素を変更しない固定物保護域。
- `navigation_observed_ground_mask.png/.json`: 地面支持セルと実測点列の指紋。
- `navigation_reviewed.json`: 入出力の指紋と変更数。PNG は PGM と同じ画素。

各種マスクは全域地図の検算用で、map_server が読む地図は `navigation_cityhall.yaml` である。
入力点群や原地図を更新した場合は、手動範囲・差分マスク・経路も再確認する。

市役所用の範囲は X `[-5, 175]` m、Y `[-120, 35]` m、1800 x 1550 セル。
PGM/PNG の画素は全域地図の対応する長方形と完全に同じで、追加の塗り替えはない。
YAML の原点を `[-5, -120, 0]` とし、GLIM 世界座標の位置は変えない。
自己位置地図とは画像サイズ・画像原点が異なるが、地図フレームは同じ。
`navigation_cityhall.json` に切り出し位置と両画像の指紋を残し、
回帰テストでは画素一致と座標の一致を独立に確認する。

編集マスク・固定物保護・地面支持距離・PNG/PGM 一致を含む地図テストと、
設定・launch の ROS テスト 46 件を確認した。3 パッケージを再ビルドした後、
実機時刻とシミュレーション時刻の両方で、新しい `/map` と変更していない
`/map_loc`、分離した 2 系統の scan が配信されることを確認した。
これらは合成入力による配線試験で、機体の走行試験ではない。

初期の VI 到着半径 0.3 m は、0.2 m の計画格子では到着セル集合が小さすぎ、
周囲約 1.6 m が自由な西側の 1 m 区間でも `NoAction` を返した。
PGM の画素を保って原点だけを 0 にした対照試験でも同様だったが、
到着半径だけを 0.45 m にすると同じ区間の実 VI 計画が成功した。
2026 設定は 0.45 m とし、自由なゴール周囲に 2 x 2 の到着セルを確保できることを
サブセル位置を変えた回帰テストで確認する。固定物を消したり、未観測全体を
自由へ変更したりする対処はしていない。
角度も、30 度刻みの回転行動と 6 度刻みの格子に対して到着幅 ±15 度では
到達不能な位相があった。±18 度でも浮動小数点の境界で 120 度がセル 19 となり、
150 度との往復に入ったため、両端に 1 セルの余裕を取って ±24 度とする。
同じ 180 度から 135 度への据え切り要求は、この変更で実 VI の計画が成功した。
全 360 個の整数目標角について、端のセルを除いても全行動位相が到着セルを持つことを検算する。
並進行動は前後とも 0.15 m とする。0.1 m 以下では斜め方向の同一セル遷移が残り、
0.3 m では薄い占有セルを飛び越えるため、`√2 x セル幅` 以上で、
隣接セルのサブセル標本を飛ばさない長さを検算する。
行動長は速度指令でもあるので、VI の並進指令は最大 0.15 m/s となる。

### 市役所一周の参照経路と検証

`cityhall_route_check.json` に、地図の指紋、実際の車体外形と検証範囲を記録する。
走行指令を出さない実 VI の計画試験では、到着角 ±18 度の設定で参照動作の先頭 6 区間が
成功し、その返却経路も車体外形で非衝突だった。ただし継続試験では先頭 13 区間の
返却経路に車体接触があり、14 番目の据え切りが `LoopDetected` となった。
到着角 ±24 度でこの据え切り単体は成功したが、接触の解消や一周の成功を示すものではない。
**静的に通れる参照経路はあるが、実 VI による安全な一周と機体の実走行は未確認。**
固定物をさらに消して計画器の失敗を隠す修正は行わない。

2 x 2 の縮小では南東の `(143.2, -84.0)` 付近に約 0.447 m の隙間しか残らず、
一周時の padding 外側の余裕が最大でも約 3.6 mm となる。
元点群の約 0.29..0.37 m の低い返りは動体と断定できないため残し、
固定物を消す代わりに `map_scale: 1` で元の 0.1 m 格子を維持する。

`cityhall_loop_reference.json` は、元格子上で検算した約 465.10 m の閉じた参照経路。
GLIM 地図座標の `[x, y, yaw]` を始点・終点とする 146 動作からなり、
**前後進と実際の base_footprint 基準の据え切りだけ**を使う。横移動は含まない。
車体の後方オフセット、0.01 m の footprint padding と、追加 0.03 m の静的余裕を含め、
未知セルも障害物として全動作を独立した回帰テストで検算する。
直進は掃引矩形、旋回は各角度区間全体を覆う矩形で確認し、中心線や離散点だけの判定ではない。
始終点の一致と、市役所を一周する winding も確認する。
これは幾何学的な参照であり、VI が返す経路の一致・コントローラ追従・実機走行は別の検証である。

## 実機の起動

2025 の分離スキャン構成を参考にした専用入口を使う。
既定は実機時刻、RViz オフ、emcl2 + VI standalone、compact + greedy。
計画側の高さ上限は新地図に合わせて 2.5 m、自己位置側は 5.5 m。
計画内部も `map_scale: 1` の 0.1 m/セルとし、全域地図を二重保持しないよう
先読みは無効。`early_start` で到達経路が解けた時点で返す。
全域をこの格子で計画すると compact 出力が約 6.06 GB となり disk mmap へ落ちたため、
市役所用の範囲で約 2.01 GB に抑え、RAM 上限 4096 MiB の既定内で扱う。
全域の手修正地図と全域の自己位置地図は保存している。
パラメータの現地適合と実機走行は未確認。

依存と新規ファイルを反映するため、実機で再ビルドする。
既存の navigation / mapping は終了し、robot_bringup のドライバ・EKF は動かしておく。

```bash
docker compose build
docker compose up -d
docker compose exec ros2 /ros_entrypoint.sh \
  ros2 launch daifuku_stack navigation_tsukuba2026.launch.py
```

`/livox/lidar`、`/odom`、`odom -> base_footprint` と LiDAR の TF が入力。
実機では TF 投影前に両方の点群を受信時刻へ補正する。ドライバはこの入口では立てない。
`src/daifuku_config/site` は自動で変更しない。
初期位置は GLIM の地図座標で `/initialpose` に与える。表示が必要なときだけ
`use_rviz:=true` を添え、2D Pose Estimate で現在位置を指定する。

時刻補正なしで点群バッグ等を使う場合:

```bash
ros2 launch daifuku_stack navigation_tsukuba2026.launch.py use_sim_time:=true
```

この場合は `/clock` と同じ座標系・時刻系の入力 TF が必要。
`localization_gravity` は odom の roll/pitch だけから作る。既定の実機 EKF が
`two_d_mode: true` の場合は傾きが 0 で、別途 IMU 姿勢推定を行うものではない。
